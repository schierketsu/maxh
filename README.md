# мера — меры господдержки и поиск партнёров для малого бизнеса в MAX

Чат-бот в MAX с подключённым мини-приложением. Трек «Эффективный бизнес».

|                     |                                                                            |
| ------------------- | -------------------------------------------------------------------------- |
| **Чат-бот**         | `@t215_hakaton_max_bot` — найдите в MAX и отправьте `/start`               |
| **Мини-приложение** | <https://hackmax.ru> — открывается из бота, работает и в браузере          |
| **Стенд**           | Развёрнут и доступен: основной сценарий проверяется без локального запуска |

---

## Быстрый старт

Две команды из корня репозитория. Значения ключей — на первом слайде
презентации.

**PowerShell (Windows):**

```powershell
[IO.File]::WriteAllText("$PWD\.env", (@("MAX_BOT_TOKEN=ВСТАВЬТЕ","DADATA_API_KEY=ВСТАВЬТЕ","CLOUDRU_API_KEY=ВСТАВЬТЕ","MINIAPP_URL=","MAX_API_BASE=https://platform-api.max.ru","BOT_POLLING=off","VITE_YANDEX_MAPS_API_KEY=ВСТАВЬТЕ","VITE_API_BASE_URL=","MINIAPP_PORT=8080") -join "`n") + "`n", (New-Object Text.UTF8Encoding $false))
docker compose up --build

```

ВНИМАНИЕ ВОЗЬМИТЕ ПОДПРАВЛЕННЫЙ СКРИПТ ИЗ ПРЕЗЕНТАЦИИ

**bash (Linux / macOS / Git Bash):**

```bash
printf '%s\n' 'MAX_BOT_TOKEN=ВСТАВЬТЕ' 'DADATA_API_KEY=ВСТАВЬТЕ' 'CLOUDRU_API_KEY=ВСТАВЬТЕ' 'MINIAPP_URL=' 'MAX_API_BASE=https://platform-api.max.ru' 'BOT_POLLING=off' 'VITE_YANDEX_MAPS_API_KEY=ВСТАВЬТЕ' 'VITE_API_BASE_URL=' 'MINIAPP_PORT=8080' > .env
docker compose up --build
```

Мини-приложение откроется на <http://localhost:8080>. Сборка занимает около
30 секунд. Если порт занят, поменяйте `MINIAPP_PORT` в `.env`.

Нужен интерактивный ввод — в репозитории лежат `setup-env.sh` и
`setup-env.ps1`: спросят каждый ключ и создадут тот же `.env`.

> **Чат-бот при локальном запуске.** Long polling к MAX должен вести ровно
> один процесс: два клиента с одним токеном делят апдейты между собой, и
> ответы приходят то дважды, то ни разу. Бот уже работает на стенде, поэтому
> локально polling выключен (`BOT_POLLING=off`) — HTTP API поднимается,
> мини-приложение работает целиком. **Чат проверяйте на боте по ссылке
> выше.** Чтобы поднять чат локально, поставьте `BOT_POLLING=on`, но стенд
> тогда придётся остановить.

## Что это и для кого

**Пользователь:** владелец микро- или малого предприятия (ООО или ИП до
15 человек) в общественном питании и производстве продуктов — кофейни,
кондитерские, пекарни, кейтеринг.

**Проблема:** предпринимателю нужны деньги на развитие или поставщик под
конкретную задачу. Меры поддержки разложены по десяткам порталов с разными
правилами отбора, поставщиков ищут вручную по чатам и знакомым. Подходящая
субсидия остаётся неиспользованной, а закупка затягивается.

**Что делает продукт:**

1. По ИНН определяет профиль компании (регион, ОКВЭД, возраст, статус МСП) и
   показывает только те меры поддержки, под которые компания подходит — с
   разбором требований и отслеживанием статуса поданной заявки.
2. Ведёт B2B-сеть: заявка описывается свободным текстом, языковая модель
   раскладывает её на поля, компании с подходящим ОКВЭД получают уведомление
   в чат и предлагают цену, не выходя из MAX.
3. Показывает партнёров и чужие заявки на карте с персональной
   рекомендацией, подобранной по профилю компании.

## Основной пользовательский сценарий

От «мне нужен поставщик» до полученного предложения, целиком внутри MAX:

1. Пользователь открывает бота и отправляет `/start`.
2. Выбирает демо-компанию (`/demo`) или вводит ИНН. Бот запоминает связку
   «MAX-аккаунт → компания».
3. Открывает мини-приложение — оно узнаёт пользователя через MAX Bridge и
   входит без повторной авторизации.
4. Описывает потребность обычным текстом: «нужно 40 кг арабики в месяц,
   бюджет до 180 тысяч».
5. Языковая модель раскладывает текст на позицию, количество, срок, бюджет.
6. Компании с подходящим ОКВЭД получают уведомление в чат MAX.
7. Поставщик нажимает «предложить цену» прямо в чате.
8. Заявитель получает предложение в чат и видит его в списке своих заявок.

## Пошаговый сценарий проверки

### A. B2B-кооперация — приоритетный сценарий

Проходится в чате бота, мини-приложение не нужно.

| Шаг | Действие                                                  | Ожидаемый результат                                                                     |
| --- | --------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| 1   | Открыть бота, отправить `/start`                          | Приветствие и предложение выбрать компанию. Кнопок разделов ещё нет                     |
| 2   | `/demo` → «ВКУСНЫЙ КЕЙК»                                  | «Вы вошли как **ВКУСНЫЙ КЕЙК**», появляется меню разделов                               |
| 3   | «партнёры рядом» → «мне что-то нужно»                     | Поле свободного ввода                                                                   |
| 4   | Ввести «нужно 40 кг арабики в месяц, бюджет до 180 тысяч» | Модель разложила текст: позиция «арабика», количество «40 кг в месяц», бюджет 180 000 ₽ |
| 5   | Подтвердить                                               | Заявка создана, в ответе число уведомлённых компаний                                    |
| 6   | `/demo` → «КОФЕ ТОЧКА»                                    | «Аккаунт переключён: **ВКУСНЫЙ КЕЙК** → **КОФЕ ТОЧКА**»                                 |
| 7   | «партнёры рядом» → «возможности»                          | В списке видна заявка из шага 5                                                         |
| 8   | «предложить цену», ввести цену и условия                  | Предложение отправлено                                                                  |
| 9   | Вернуться на «ВКУСНЫЙ КЕЙК», «мои заявки»                 | У заявки одно предложение с ценой из шага 8                                             |

Сценарий проходится в одиночку за счёт двух демо-компаний: заявка создаётся
под одной, ответ приходит под другой.

| ИНН          | Название в продукте | Профиль                   |
| ------------ | ------------------- | ------------------------- |
| `7724351831` | ВКУСНЫЙ КЕЙК        | Кондитерская, рейтинг 4,7 |

## Примеры ожидаемого поведения

**Разбор заявки языковой моделью.** Ввод: `нужно 40 кг арабики в месяц,
бюджет до 180 тысяч, до конца октября` →

```json
{
  "item": "зерновой кофе (арабика)",
  "qty": "40 кг в месяц",
  "budget": 180000,
  "deadline": "2026-10-31"
}
```

**Поиск компании по ИНН.** `GET /api/company/7724351831` →

```json
{
  "company": {
    "inn": "7724351831",
    "name": "ООО \"ТОРТЫ МОСКВА\"",
    "region": "г Москва",
    "okved": ["56.10"],
    "isSme": true
  }
}
```

**Ошибки:**

| Ситуация                  | Поведение                                                                                  |
| ------------------------- | ------------------------------------------------------------------------------------------ |
| Несуществующий ИНН        | `404 {"error": "Компания не найдена"}`, поле подсвечивается, ввод доступен снова           |
| DaData недоступна         | `502 {"error": "Не удалось получить данные компании"}`                                     |
| Модель не разобрала текст | «Не удалось разобрать текст, попробуйте переформулировать», диалог остаётся на том же шаге |
| Cloud.ru недоступен       | Рекомендации молча откатываются на эвристику по ОКВЭД                                      |
| Ключ не задан             | Бот сообщает об этом при старте и работает без этой функции                                |

## Архитектура

```
maxh/
├── compose.yaml            запуск всего решения одной командой
├── .env                    ключи (создаётся при старте, в git не попадает)
├── bot/                    Node.js 22, без фреймворков
│   ├── src/index.js        long polling MAX + маршрутизация команд
│   ├── src/max.js          клиент MAX Bot API
│   ├── src/server.js       HTTP API для мини-приложения (порт 3001)
│   ├── src/b2bChat.js      многошаговые диалоги B2B в чате
│   ├── src/b2bStore.js     хранилище: компании, заявки, предложения, привязки
│   ├── src/b2bNotify.js    уведомления в чат
│   ├── src/recommend.js    подбор заявки: эмбеддинги + реранкер
│   ├── src/llm.js          разбор заявки свободным текстом
│   ├── src/dadata.js       профиль компании по ИНН
│   ├── src/matching.js     правила отбора мер поддержки
│   └── data/b2b.json       файловое хранилище
└── miniapp/                React 19 + TypeScript + Vite
    ├── src/pages/          вход, главная, субсидии, карта, профиль, заявки
    ├── src/components/     карточка меры, нижняя навигация, ИНН-гейт
    ├── src/lib/            клиенты API, MAX Bridge, Яндекс.Карты
    └── src/data/           каталоги мер поддержки
```

У мини-приложения нет своего бэкенда: оно обращается к HTTP API того же
процесса, что держит long polling к MAX. Пользователь опознаётся по MAX
`user_id`, который мини-приложение получает через MAX Bridge и передаёт в
каждый запрос — поэтому вход в одном интерфейсе сразу виден в другом.

```
MAX (чат)      ──long polling──►  bot/src/index.js ──┐
                                                     ├──► b2b.json
MAX (мини-апп) ──HTTPS /api────►  bot/src/server.js ─┘
                                        │
                                        ├──► DaData
                                        ├──► Cloud.ru Foundation Models
                                        └──► MAX Bot API (уведомления)
```

**Сервисы в compose:**

| Сервис    | Образ            | Роль                                               |
| --------- | ---------------- | -------------------------------------------------- |
| `bot`     | `node:22-alpine` | Long polling и HTTP API на порту 3001              |
| `miniapp` | `caddy:2-alpine` | Статика мини-приложения плюс прокси `/api` на бота |

Наружу публикуется только `miniapp`. API доступен через него по тому же
адресу, поэтому мини-приложение обращается к нему относительным путём и
кросс-доменных запросов не возникает.

## Переменные окружения

Все в одном файле `.env` в корне: его читают docker compose, бот при запуске
без Docker и Vite при сборке мини-приложения. Шаблон — `.env.example`.

| Переменная                 | Обязательна   | Назначение                                            |
| -------------------------- | ------------- | ----------------------------------------------------- |
| `MAX_BOT_TOKEN`            | да            | Токен чат-бота                                        |
| `DADATA_API_KEY`           | да            | DaData: профиль компании по ИНН                       |
| `CLOUDRU_API_KEY`          | нет           | Cloud.ru: разбор заявок и рекомендации                |
| `VITE_YANDEX_MAPS_API_KEY` | да            | Yandex Maps JS API v3 для экрана карты                |
| `MAX_API_BASE`             | рекомендуется | Адрес MAX API, см. ниже                               |
| `BOT_POLLING`              | нет           | `on`/`off` — вести ли long polling. В compose `off`   |
| `MINIAPP_URL`              | нет           | Публичный адрес мини-приложения для кнопок `open_app` |
| `MINIAPP_PORT`             | нет           | Порт мини-приложения, по умолчанию 8080               |
| `VITE_API_BASE_URL`        | нет           | Адрес API. Пусто — текущий origin                     |
| `ALLOWED_ORIGINS`          | нет           | Дополнительные origin для CORS, через запятую         |
| `PORT`                     | нет           | Порт HTTP API, по умолчанию 3001                      |

Без `CLOUDRU_API_KEY` решение остаётся работоспособным: меры поддержки и
профиль компании не затрагиваются, создание заявки свободным текстом
перестаёт работать, рекомендации откатываются на эвристику по ОКВЭД.

`MAX_API_BASE` важен для безопасности: `platform-api2.max.ru` отдаёт
сертификат Минцифры, которого нет в стандартных хранилищах, и ради него
клиент отключает проверку TLS. `platform-api.max.ru` обслуживает тот же
контракт с обычным сертификатом — на стенде используется он, проверка TLS
работает в полном объёме.

Ключ Яндекс.Карт ограничен по HTTP Referer в кабинете Яндекса и попадает в
собранный бандл — это параметр сборки, а не секрет. Остальные ключи —
настоящие секреты, в репозиторий не попадают.

| Порт | Компонент                                         |

| 8080 | Мини-приложение (переопределяется `MINIAPP_PORT`) |
| 3001 | HTTP API бота, внутри сети compose                |

подойдёт, используйте стенд.

## Работа с данными

**Серверное хранилище** — `bot/data/b2b.json`, читается в память при старте и
переписывается при изменении.

| Ключ                  | Содержимое                                              |
| --------------------- | ------------------------------------------------------- |
| `companies`           | Кэш профилей DaData по ИНН                              |
| `requests`            | Заявки B2B: позиция, количество, срок, бюджет, владелец |
| `offers`              | Предложения по заявкам: цена, условия, ИНН поставщика   |
| `testers`             | Связка `MAX user_id → ИНН`                              |
| `benefitApplications` | Заявки на меры поддержки: мера, владелец, время подачи  |

Заявки принадлежат конкретному MAX-аккаунту, а не ИНН: двое проверяющих,
выбравших одну демо-компанию, работают в независимых песочницах и не видят
заявок друг друга.

**Хранилище мини-приложения** — `localStorage`, только вспомогательные
состояния: текущая компания и отклики «вы связывались». Всё, что должен
видеть бот, лежит на бэкенде.

Кэш профилей DaData — 10 минут. Эмбеддинги заявок кэшируются в памяти
процесса.

### Тестовые данные

Хранилище создаётся само при первом запуске и засеивается восемью витринными
заявками — отдельная команда не нужна. Сброс к исходному состоянию:

```bash
rm bot/data/b2b.json          # PowerShell: Remove-Item bot/data/b2b.json
docker compose restart bot
```

## Известные ограничения

**Запуск**

- Один токен — один процесс с long polling: локальный чат и стенд
  одновременно работать не могут (см. `BOT_POLLING`).

**Продукт**

- Авторизация через Госуслуги не реализована — вместо неё переключатель
  демо-компаний.
- Заявка на меру регистрируется в продукте и видна в боте, но в ведомство не
  отправляется: канала подачи у MVP нет.
- Этапы обработки заявки наступают по таймеру, а не по событиям реальной
  системы.
- Уведомление о новой заявке доходит только до компаний, которые хотя бы раз
  писали боту — иначе у продукта нет их MAX `user_id`.
- Один MAX-аккаунт представляет одну компанию одновременно.
- Каталог мер поддержки обновляется вручную: даты, лимиты и условия могут
  разойтись с первоисточником.

**Техника**

- Хранилище — файл JSON без блокировок. Для MVP достаточно, при нескольких
  параллельных процессах возможна потеря записи.
- Диалоги в чате хранятся в памяти процесса: после перезапуска бота
  незавершённый ввод теряется. Созданные заявки не затрагиваются.
- Иконки мини-приложения не оптимизированы: несколько PNG весят около
  мегабайта каждая.

## Управление

```bash
docker compose up --build     # запустить
docker compose stop           # остановить, сохранив контейнеры
docker compose start          # запустить снова
docker compose down           # остановить и удалить контейнеры
docker compose logs -f bot    # логи бота
```

Данные переживают перезапуск: они лежат в томе `./bot/data`.

### Запуск без Docker

```bash
cd bot && npm ci --omit=dev && npm start      # бот и API на порту 3001
cd miniapp && npm ci && npm run dev           # мини-апп на порту 5173
```

Vite в режиме разработки проксирует `/api` на `localhost:3001`, переменные
`VITE_*` берёт из того же корневого `.env`.
