# Мера — сервис мер поддержки и B2B-кооперации для малого бизнеса в MAX

Хакатон «Эффективный бизнес», трек Минобрнауки × MAX.
Решение: **чат-бот в MAX с подключённым мини-приложением**.

---

## 1. Назначение решения

**Пользователь:** владелец или управляющий микро- и малого предприятия
(ООО или ИП до 15 человек) в сфере общественного питания и производства
продуктов питания — кофейни, кондитерские, пекарни, кейтеринг.

**Проблема:** предприниматель в ситуации, когда ему нужны деньги на
развитие или поставщик под конкретную задачу, хочет быстро понять, что
именно ему доступно, но сталкивается с тем, что меры поддержки разложены
по десяткам порталов с разными правилами отбора, а поставщиков приходится
искать вручную по чатам и знакомым, — из-за чего подходящая субсидия
остаётся неиспользованной, а закупка затягивается.

**Что делает продукт:**

1. По ИНН определяет профиль компании (регион, ОКВЭД, возраст, статус МСП)
   и показывает только те меры поддержки, под которые компания подходит,
   с разбором требований и отслеживанием статуса поданной заявки.
2. Ведёт локальную B2B-сеть: заявка описывается свободным текстом, языковая
   модель раскладывает её на поля, а компании с подходящим ОКВЭД получают
   уведомление в чат и могут предложить цену, не выходя из MAX.
3. Показывает партнёров и чужие заявки на карте с персональной
   рекомендацией, подобранной по профилю компании.

---

## 2. Основной пользовательский сценарий

Приоритетный сценарий — **от «мне нужен поставщик» до полученного
предложения, целиком внутри MAX**:

1. Пользователь открывает бота `@t215_hakaton_max_bot` и отправляет `/start`.
2. Выбирает демо-компанию (`/demo`) или вводит реальный ИНН. Бот
   запоминает связку «MAX-аккаунт → компания».
3. Открывает мини-приложение — оно узнаёт пользователя через MAX Bridge и
   входит без повторной авторизации.
4. В разделе «партнёры рядом» описывает потребность обычным текстом
   («нужно 40 кг арабики в месяц, бюджет до 180 тысяч»).
5. Языковая модель раскладывает текст на позицию, количество, срок и
   бюджет; пользователь подтверждает.
6. Компании с подходящим ОКВЭД получают уведомление в чат MAX.
7. Поставщик нажимает «предложить цену» прямо в чате и отправляет условия.
8. Заявитель получает предложение в чат и видит его в списке своих заявок.

Второй сценарий — **меры поддержки**: «Государственные субсидии» → список
подходящих программ → «Подробнее» → условия и требования → «подать
заявку» → статус заявки с историей этапов → заявка видна в разделе
«заявки».

## 3. Состав и архитектура решения

```
maxh/
├── bot/                    Node.js, без фреймворков
│   ├── src/index.js        точка входа: long polling MAX + маршрутизация команд
│   ├── src/max.js          клиент MAX Bot API (отправка, клавиатуры, апдейты)
│   ├── src/server.js       HTTP API для мини-приложения (порт 3001)
│   ├── src/b2bChat.js      многошаговые диалоги B2B прямо в чате
│   ├── src/b2bStore.js     хранилище: компании, заявки, предложения, привязки
│   ├── src/b2bNotify.js    уведомления в чат о заявках, предложениях, входе
│   ├── src/recommend.js    подбор чужой заявки: эмбеддинги + реранкер
│   ├── src/embeddings.js   Cloud.ru: bge-m3 и bge-reranker-v2-m3
│   ├── src/llm.js          Cloud.ru: разбор заявки свободным текстом
│   ├── src/dadata.js       DaData: профиль компании по ИНН
│   ├── src/matching.js     правила отбора мер поддержки под профиль
│   ├── src/benefits.js     каталог мер поддержки (данные)
│   ├── src/demo*.js        витринные данные: бренды, профили, уведомления
│   └── data/b2b.json       файловое хранилище (создаётся при первом запуске)
└── miniapp/                React 19 + TypeScript + Vite
    ├── src/pages/          экраны: вход, главная, субсидии, карта, профиль, заявки
    ├── src/components/     карточка меры, нижняя навигация, ИНН-гейт
    ├── src/lib/            клиенты API, MAX Bridge, Яндекс.Карты, localStorage
    ├── src/data/           каталоги мер поддержки и демо-уведомлений
    └── src/context/        текущая компания (React Context + localStorage)
```

**Связь компонентов.** Бот и мини-приложение работают поверх одного
хранилища `bot/data/b2b.json`. Мини-приложение не имеет своего бэкенда: оно
обращается к HTTP API того же процесса, что держит long polling к MAX.
Пользователь опознаётся по MAX `user_id`, который мини-приложение получает
через MAX Bridge и передаёт в каждый запрос, — поэтому вход в одном
интерфейсе сразу виден в другом.

```
MAX (чат)  ──long polling──►  bot/src/index.js ──┐
                                                 ├──► b2bStore (b2b.json)
MAX (мини-апп) ──HTTPS /api──► bot/src/server.js ┘
                                    │
                                    ├──► DaData (профиль по ИНН)
                                    ├──► Cloud.ru Foundation Models (LLM, эмбеддинги)
                                    └──► MAX Bot API (уведомления в чат)
```

## 4. Запуск через Docker

Всё решение поднимается одной командой.

```bash
cp bot/.env.example bot/.env      # ключи бота: токен MAX, DaData, Cloud.ru
cp .env.example .env              # ключ Яндекс.Карт для сборки мини-аппа
docker compose up --build
```

После старта:

- мини-приложение — <http://localhost:8080>
- чат-бот подключается к MAX сам и отвечает в чате

Если порт 8080 занят, укажите другой в `.env`: `MINIAPP_PORT=8099`.

> **Важно про чат-бота.** На боевом стенде бот уже ведёт long polling к MAX.
> Два клиента с одним токеном делят апдейты между собой — ответы приходили бы
> то дважды, то ни разу. Поэтому в compose локальный polling по умолчанию
> выключен (`BOT_POLLING=off`): HTTP API поднимается, мини-приложение
> работает целиком, а чат проверяется на боевом боте по ссылке из первого
> слайда презентации.
>
> Чтобы поднять чат локально, поставьте `BOT_POLLING=on` в `.env` — но тогда
> боевого бота нужно остановить, иначе будут дубли.

**Состав:**

| Сервис | Образ | Что делает |
|---|---|---|
| `bot` | `node:22-alpine` | Long polling к MAX и HTTP API на порту 3001 |
| `miniapp` | `caddy:2-alpine` | Собранная статика плюс прокси `/api` на бота |

Наружу публикуется только `miniapp`. API доступен через него по тому же
адресу (`/api/...`), поэтому мини-приложение обращается к нему
относительным путём и кросс-доменных запросов не возникает.

Данные бота лежат в томе `./bot/data` — заявки и связки аккаунтов переживают
пересоздание контейнеров.

**Проверено:** сборка обоих образов занимает около 30 секунд (лимит — 5 минут),
итоговые образы 244 МБ и 104 МБ.

**Остановка и повторный запуск:**

```bash
docker compose stop           # остановить, сохранив контейнеры
docker compose start          # запустить снова
docker compose down           # остановить и удалить контейнеры
docker compose logs -f bot    # логи бота
```

### Запуск без Docker

```bash
cd bot && npm ci --omit=dev && npm start      # бот и API на порту 3001
cd miniapp && npm ci && npm run dev           # мини-апп на порту 5173
```

Vite в режиме разработки сам проксирует `/api` на `localhost:3001`
(см. `miniapp/vite.config.ts`), поэтому `VITE_API_BASE_URL` остаётся пустым.

## 5. Параметры окружения

### `bot/.env`

| Переменная | Обязательна | Назначение |
|---|---|---|
| `MAX_BOT_TOKEN` | да | Токен чат-бота, выдаётся организаторами |
| `DADATA_API_KEY` | да | DaData: профиль компании по ИНН |
| `CLOUDRU_API_KEY` | нет | Cloud.ru Foundation Models: разбор заявок и рекомендации |
| `MINIAPP_URL` | нет | Публичный адрес мини-приложения для кнопок `open_app` |
| `PORT` | нет | Порт HTTP API, по умолчанию `3001` |
| `BOT_POLLING` | нет | `on`/`off` — вести ли long polling к MAX. В compose по умолчанию `off` |
| `ALLOWED_ORIGINS` | нет | Дополнительные origin для CORS, через запятую |
| `MAX_API_BASE` | рекомендуется | Базовый адрес MAX API. Укажите `https://platform-api.max.ru` — см. ниже |

Адрес MAX API важен для безопасности: `platform-api2.max.ru` отдаёт
сертификат Минцифры, которого нет в стандартных хранилищах, и ради него
клиент отключает проверку TLS. `platform-api.max.ru` обслуживает тот же
контракт с обычным сертификатом — на боевом стенде используется он,
и проверка TLS работает в полном объёме.

Без `CLOUDRU_API_KEY` продукт остаётся работоспособным: меры поддержки и
профиль компании не затрагиваются, создание заявки свободным текстом
перестаёт работать, а рекомендации молча откатываются на эвристику по
совпадению ОКВЭД.

### `miniapp/.env`

| Переменная | Обязательна | Назначение |
|---|---|---|
| `VITE_API_BASE_URL` | нет | Базовый адрес API бота. Пусто — запросы к текущему origin |
| `VITE_YANDEX_MAPS_API_KEY` | да | Yandex Maps JS API v3 для экрана карты |

Ключ Яндекс.Карт ограничен по HTTP Referer в кабинете Яндекса и всё равно
попадает в собранный бандл — это параметр сборки, а не секрет. Остальные
ключи — настоящие секреты и в репозиторий не попадают: `.env` обоих
пакетов и каталог `in_help/` перечислены в `.gitignore`.

### Порты

| Порт | Компонент |
|---|---|
| `3001` | HTTP API бота (переопределяется `PORT`) |
| `5173` | Vite dev-сервер мини-приложения |
| `80`, `443` | Caddy на продакшн-сервере: статика мини-аппа и прокси `/api/*` на 3001 |

## 8. Работа с данными

**Серверное хранилище** — `bot/data/b2b.json`, файл JSON, читается в память
при старте и переписывается при каждом изменении. Структура:

| Ключ | Содержимое |
|---|---|
| `companies` | Кэш профилей из DaData по ИНН: название, регион, ОКВЭД |
| `requests` | Заявки B2B: позиция, количество, срок, бюджет, `ownerUserId` |
| `offers` | Предложения по заявкам: цена, условия, ИНН поставщика |
| `testers` | Связка `MAX user_id → ИНН`: какую компанию представляет аккаунт |
| `benefitApplications` | Заявки на меры поддержки: мера, владелец, время подачи |

Разделение по `ownerUserId` существенно: заявки принадлежат конкретному
MAX-аккаунту, а не ИНН. Два человека, выбравшие одну демо-компанию,
работают в независимых песочницах и не видят заявок друг друга.

**Хранилище мини-приложения** — `localStorage` браузера, с ключами по ИНН:

| Ключ | Содержимое |
|---|---|
| `mera.company` | Текущая компания, чтобы не входить заново при каждом открытии |
| `mera.contactedRequests.<инн>` | Заявки, по которым пользователь связывался |

Данные в `localStorage` живут только на устройстве и боту не передаются — там лежат только вспомогательные состояния. Всё, что должен видеть бот, хранится на бэкенде.
Кэш профилей DaData — 10 минут, эмбеддинги заявок кэшируются в памяти
процесса по идентификатору заявки.

уведомления о новых заявках и предложениях, связка аккаунта с компанией.

## 10. Порядок работы с тестовыми данными

Хранилище создаётся само при первом запуске бота и засеивается восемью
витринными заявками. Отдельная команда не нужна.

**Сброс к исходному состоянию:**

```bash
cd bot
rm data/b2b.json      # PowerShell: Remove-Item data/b2b.json
npm start             # файл будет создан заново и засеян
```

**Демо-компании для проверки:**

| ИНН | Название в продукте | Роль в сценарии |
|---|---|---|
| `7724351831` | ВКУСНЫЙ КЕЙК | Кондитерская, рейтинг 4,7 |
| `7717762862` | КОФЕ ТОЧКА | Кофейня, рейтинг 3,8 |

Переключение между ними в чате — командой `/demo`, в мини-приложении —
кнопкой «сменить аккаунт» на экране входа. Один MAX-аккаунт представляет
одну компанию: переключение синхронно меняет её и в боте, и в мини-аппе.

Чтобы пройти сценарий «заявка → уведомление → предложение» в одиночку,
создайте заявку под одной демо-компанией, переключитесь на вторую и
ответьте на неё.

## 11. Пошаговый сценарий проверки

### Сценарий A. B2B-кооперация (приоритетный)

| Шаг | Действие | Ожидаемый результат |
|---|---|---|
| 1 | Открыть `@t215_hakaton_max_bot`, отправить `/start` | Приветствие и предложение выбрать компанию. Кнопок разделов ещё нет |
| 2 | Отправить `/demo`, выбрать «ВКУСНЫЙ КЕЙК» | «Вы вошли как **ВКУСНЫЙ КЕЙК**», появляется меню разделов |
| 3 | Открыть мини-приложение | Экран приветствия с названием компании, через 3 секунды — главная |
| 4 | «партнёры рядом» → «мне что-то нужно» | Поле свободного ввода |
| 5 | Ввести «нужно 40 кг арабики в месяц, бюджет до 180 тысяч» | Модель раскладывает текст: позиция «арабика», количество «40 кг в месяц», бюджет 180 000 ₽ |
| 6 | Подтвердить | Заявка создана, ответ содержит число уведомлённых компаний |
| 7 | В чате переключиться на «КОФЕ ТОЧКА» (`/demo`) | «Аккаунт переключён: **ВКУСНЫЙ КЕЙК** → **КОФЕ ТОЧКА**» |
| 8 | «партнёры рядом» → «возможности» | В списке видна заявка из шага 6 |
| 9 | «предложить цену», ввести цену и условия | Предложение отправлено |
| 10 | Вернуться на «ВКУСНЫЙ КЕЙК», открыть «мои заявки» | У заявки одно предложение с ценой из шага 9 |

## 12. Примеры ожидаемого поведения

**Разбор заявки языковой моделью.** Ввод: `нужно 40 кг арабики в месяц,
бюджет до 180 тысяч, до конца октября`. Результат:

```json
{
  "item": "зерновой кофе (арабика)",
  "qty": "40 кг в месяц",
  "budget": 180000,
  "deadline": "2026-10-31"
}
```

**Поиск компании по ИНН.** `GET /api/company/7724351831`:

```json
{ "company": { "inn": "7724351831", "name": "ООО \"ТОРТЫ МОСКВА\"",
  "region": "г Москва", "okved": ["56.10"], "isSme": true } }
```

**Ошибки.** Несуществующий ИНН — `404 {"error": "Компания не найдена"}`, в
интерфейсе поле подсвечивается и остаётся доступным для повторного ввода.
Недоступность DaData — `502 {"error": "Не удалось получить данные
компании"}`. Сбой языковой модели при разборе заявки — бот отвечает «Не
удалось разобрать текст, попробуйте переформулировать» и остаётся на том же
шаге, диалог не сбрасывается. Недоступность Cloud.ru при подборе
рекомендаций — молчаливый откат на эвристику по ОКВЭД, пользователь видит
рекомендацию в обычном виде.

## 13. Известные ограничения

**Запуск**

- Один токен — один процесс с long polling. Локальный запуск чата и боевой
  стенд одновременно работать не могут (см. `BOT_POLLING`).

**Продукт**

- Авторизация через Госуслуги не реализована — вместо неё переключатель
  демо-компаний.
- Заявка на меру поддержки регистрируется в продукте и видна в боте, но
  в ведомство не отправляется: канала подачи у MVP нет.
- Этапы обработки заявки наступают по таймеру от момента подачи,
  а не по событиям реальной системы.
- Уведомление о новой заявке доходит только до компаний, которые хотя бы
  раз писали боту, — иначе у продукта нет их MAX `user_id`.
- Один MAX-аккаунт представляет одну компанию одновременно.
- Расстояние до партнёра на карте не показывается.
- Каталог мер поддержки обновляется вручную: даты, лимиты и условия могут
  разойтись с первоисточником.

**Техника**

- Хранилище — файл JSON, без блокировок. Для MVP достаточно, при
  нескольких параллельных процессах возможна потеря записи.
- Диалоги в чате хранятся в памяти процесса: после перезапуска бота
  незавершённый ввод теряется. Созданные заявки не затрагиваются.
- Клиент MAX умеет отключать проверку TLS ради `platform-api2.max.ru`
  (`bot/src/max.js`). На боевом стенде этот режим не используется:
  `MAX_API_BASE` указывает на `platform-api.max.ru` с обычным сертификатом.
- CORS ограничен списком origin (домены прода и localhost для
  разработки); расширяется переменной `ALLOWED_ORIGINS`.
- Иконки в мини-приложении не оптимизированы: два PNG весят около мегабайта.

## 14. Остановка и повторный запуск

**Локально.** Остановить процесс — `Ctrl+C` в терминале с `npm start`,
контейнер — `Ctrl+C` или `docker stop <id>`. Повторный запуск — та же
команда из раздела 4. Данные сохраняются в `bot/data/b2b.json`, состояние
восстанавливается само; теряются только незавершённые диалоги в чате.

**На сервере** (systemd, боевой стенд):

```bash
sudo systemctl stop mera-bot       # остановить
sudo systemctl start mera-bot      # запустить
sudo systemctl restart mera-bot    # перезапустить
sudo journalctl -u mera-bot -f     # смотреть логи
```

Веб-сервер с мини-приложением — `sudo systemctl restart caddy`.

После обновления кода мини-приложения нужна пересборка:

```bash
cd miniapp && npm run build
```

## 15. Внешние сервисы, не воспроизводимые в Docker

Для работы MVP необходимы внешние API, которые нельзя поднять локально:

| Сервис | Что нужно для проверки |
|---|---|
| MAX Bot API | Токен бота от организаторов в `MAX_BOT_TOKEN` |
| DaData | Бесплатный ключ с [dadata.ru](https://dadata.ru) в `DADATA_API_KEY` |
| Cloud.ru Foundation Models | Ключ в `CLOUDRU_API_KEY`; без него часть функций деградирует предсказуемо |
| Yandex Maps JS API v3 | Ключ в `VITE_YANDEX_MAPS_API_KEY`, домен проверки добавлен в ограничения по HTTP Referer |

Мини-приложение подключается к MAX только по HTTPS: для проверки в MAX
нужен публичный домен с сертификатом, `localhost` не подойдёт.
