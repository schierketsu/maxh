# Мера — чат-бот MAX

Локальный long polling к `t215_hakaton_max_bot`. Тот же процесс поднимает HTTP API
для мини-приложения (поиск компании по ИНН через DaData).

## Запуск

### Настройка секретов

Все ключи и токены — через переменные окружения. Проще всего скопировать
шаблон и заполнить его:

```bash
cd bot
cp .env.example .env    # PowerShell: Copy-Item .env.example .env
```

Откройте `bot/.env` и заполните нужные переменные (`KEY=value` построчно,
файл уже в `.gitignore` — своими значениями в git его не закоммитите):

- `MAX_BOT_TOKEN` — токен бота в MAX. Можно не задавать, если есть доступ к
  `in_help/pass.md` (токен читается оттуда как fallback).
- `DADATA_API_KEY` — ключ DaData API для поиска компаний по ИНН, бесплатный
  тариф, регистрация на [dadata.ru](https://dadata.ru).
- `CLOUDRU_API_KEY` — ключ Cloud.ru Foundation Models
  (foundation-models.api.cloud.ru, модель `openai/gpt-oss-120b` — GigaChat на
  этом шлюзе отдаёт битый JSON в function calling, проверено) для разбора
  B2B-заявок свободным текстом. Без него сама компания и господдержка
  продолжат работать — упадёт только создание новой B2B-заявки
  (`POST /api/b2b/requests`).
- `MINIAPP_URL` — опционально, публичный URL мини-аппа. Пока не используется
  ботом: вся B2B-сеть (создать заявку, посмотреть возможности, предложить
  цену) работает прямо в чате (`bot/src/b2bChat.js`), мини-апп не задеплоен
  и не зарегистрирован за ботом в кабинете разработчика. Задел на потом —
  когда мини-апп появится на `hackmax.ru` и будет привязан к боту через
  business.max.ru/self → Чат-боты → бот → ⋮ → Настройки (без этого MAX API
  отвечает 404 на кнопки типа `open_app`), можно будет снова давать на него
  ссылки из бота.

Вместо `.env` переменные можно также экспортировать в шелл напрямую:

```bash
export DADATA_API_KEY=ваш_ключ   # PowerShell: $env:DADATA_API_KEY = "..."
```

### Секреты мини-приложения

У `miniapp/` свой `.env` (тоже в `.gitignore`), по тому же принципу —
скопировать шаблон и заполнить:

```bash
cd miniapp
cp .env.example .env    # PowerShell: Copy-Item .env.example .env
```

- `VITE_API_BASE_URL` — базовый URL HTTP API бота. Пусто — относительные
  запросы к текущему origin (прод, где мини-апп и API за одним доменом).
- `VITE_YANDEX_MAPS_API_KEY` — ключ Yandex Maps JS API v3
  (api-maps.yandex.ru), кабинет разработчика Яндекса. Он ограничен по HTTP
  Referer на стороне Яндекса и всё равно виден в собранном фронтенд-бандле
  любому пользователю — это не секрет в смысле «нельзя раскрывать», а
  просто вынесенный параметр сборки, а не полноценная тайна вроде
  `CLOUDRU_API_KEY`.

### Старт процесса

```bash
cd bot
npm start
```

В MAX найдите бота **t215_hakaton_max_bot** и отправьте `/start`.

## Что попробовать

- `/start` — приветствие, просит ИНН или `/demo`. Клавиатуры (кнопок) до
  привязки компании нет намеренно — только после того, как бот узнал, от
  чьего имени говорит пользователь, показываются три раздела.
- `/demo` — две демо-компании (те же, что в переключателе аккаунтов
  мини-аппа: «ВКУСНЫЙ КЕЙК», «КОФЕ ТОЧКА»)
- любой реальный ИНН (10 или 12 цифр)
- После привязки — три кнопки:
  - **🌐 B2B-сеть** — создать заявку (свободным текстом, LLM сам разбирает
    на поля), посмотреть свои заявки и предложения по ним, посмотреть чужие
    открытые заявки и предложить цену — полностью в чате, шаг за шагом
    (`bot/src/b2bChat.js`)
  - **👤 Профиль** — имя компании, ИНН, регион/отрасль, кнопка «сменить
    компанию» (отвязывает текущий ИНН от вашего MAX-аккаунта)
  - **🏛 Государственные субсидии** — те же 3–5 подобранных программ, что
    раньше показывались только один раз при вводе ИНН, теперь доступны
    отдельным пунктом меню в любой момент

## Как бот запоминает, кто с ним говорит — личная песочница на тестера

Бот и мини-апп делят одну и ту же карту MAX `user_id` → ИНН
(`bot/data/b2b.json`, ключ `testers`, функции `linkUser`/`getCompanyByUserId`
в `b2bStore.js`). Это отдельная карта, а не поле на самой компании — важно,
потому что демо-компаний всего две, а тестеров на защите может быть
сколько угодно, и каждый заходит под своим MAX-аккаунтом:

1. Когда пользователь присылает боту ИНН (или выбирает демо-компанию),
   `handleInn` сохраняет связку `user_id → ИНН` именно для этого
   `user_id` — выбор той же демо-компании другим тестером её не трогает.
2. Дальше любое действие — открыть B2B-сеть, посмотреть профиль,
   пересмотреть субсидии — ищет компанию по `user_id` заново, повторно
   вводить ИНН не нужно, пока не нажата «Выйти из аккаунта» (снимает связку
   только для этого `user_id`).
3. Заявки/предложения помечаются `ownerUserId` — тем самым MAX `user_id`,
   который их создал. «Мои заявки», лента «Возможности» и уведомления о
   предложениях фильтруются по нему, а не по ИНН: два тестера, выбравшие
   одну и ту же демо-компанию, работают в полностью независимых
   песочницах и не видят заявок друг друга. Единственное исключение —
   сид-демо-заявки (без `ownerUserId`) видны всем, чтобы лента не была
   пустой, и заявки, созданные тем же тестером под ДРУГОЙ его демо-личностью
   (можно соло-продемонстрировать цикл заявка→уведомление→предложение,
   переключаясь между двумя демо-компаниями). MAX-пуш о новой заявке
   отправляется только реальным (не демо) компаниям — у демо-ИНН нет
   одного однозначного владельца, пушить туда было бы утечкой между
   песочницами.
4. Та же связка и та же песочница используются и в мини-аппе через MAX
   Bridge (`GET /api/company/by-user/:userId`, `POST
   /api/company/:inn/link-user`, плюс `userId` в B2B-эндпоинтах ниже) —
   когда мини-апп будет зарегистрирован за ботом (business.max.ru/self) и
   станет открываться из чата, он узнает того же пользователя и увидит те
   же «свои» заявки без повторного входа, никакой отдельной логики на
   стороне мини-аппа заводить не придётся. Уже сейчас `lib/maxBridge.ts`
   (`getMaxUserId()`) передаёт `user_id` во все B2B-запросы мини-аппа —
   код готов, просто пока `userId` внутри MAX не задан, так как мини-апп
   открывается напрямую в браузере, не через бота.

Демо-аккаунты на главном экране мини-аппа (переключатель «сменить
аккаунт») — отдельная, чисто презентационная штука: к реальным MAX
user_id она не привязывается (в отличие от тех же демо-компаний,
выбранных через `/demo` в чате или ИНН-гейт мини-аппа — там привязка
обычная, через ту же песочницу).

## HTTP API для мини-приложения

Слушает `http://localhost:3001` (порт — переменная `PORT`).

- `GET /api/company/:inn` → `{ company }` или `404 { error }`, если компания
  не найдена. Ответы кэшируются на 10 минут.
- `GET /api/company/by-user/:userId` → `{ company }` компании, уже
  привязанной к этому MAX `user_id`, или `404`, если связки ещё нет.
- `POST /api/company/:inn/link-user` `{ userId }` → сохраняет связку
  ИНН↔MAX user_id (та же, что использует бот) → `{ ok: true }`.
- `POST /api/b2b/requests` `{ inn, text, userId? }` → LLM разбирает текст в
  заявку, помечает её `userId`-тестером, подходящим по ОКВЭД реальным
  компаниям уходит уведомление → `{ request, notified }`.
- `GET /api/b2b/opportunities?inn=X&userId=Y` → сид-демо + чужие живые
  заявки только того же тестера `userId` под другой его демо-личностью →
  `{ opportunities }`. Без `userId` видны только сид-демо.
- `GET /api/b2b/my-requests?inn=X&userId=Y` → заявки от этого ИНН,
  созданные именно тестером `userId`, с полученными предложениями →
  `{ requests }`. Без `userId` — пусто.
- `POST /api/b2b/requests/:id/offers` `{ inn, price, terms }` → сохраняет
  предложение, уведомляет заявителя (`request.ownerUserId`) → `{ offer }`.
- `GET /api/b2b/requests/:id` → одна заявка → `{ request }`.

Данные B2B (заявки/предложения/связка компания↔MAX user_id) хранятся в
`bot/data/b2b.json` — создаётся и сеется демо-заявками при первом запуске,
в git не попадает. Уведомление в MAX доходит только до компаний, которые
хотя бы раз писали боту (иначе у нас просто нет их user_id) — это
ограничение платформы, а не баг.

На этой Windows `platform-api2.max.ru` падает на сертификате Минцифры, поэтому клиент сначала пробует api2 (без проверки TLS), иначе переключается на `platform-api.max.ru`.
